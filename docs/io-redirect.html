IO 重定向

为什么需要重定向

多开场景下，多个 Guest 共享宿主 UID，不能直接写系统真实的 /data/data/<guest>。BBA 把路径拆成两层视图：

逻辑路径

Guest 看到的标准 Android 路径，例如 /data/user/0/com.example.app。

物理路径

宿主包下的虚拟根，例如 .../<host>/v0/data/user/0/com.example.app。

改写时机

open / list / create 之前，把逻辑前缀换成物理前缀，Guest 无感。

这不是内核 mount：普通 App 没有 CAP_SYS_ADMIN，也过不了 SELinux。BBA 走的是「路径字符串改写」路线。

架构：双通道、单真相源

物理根：v0

BEnvironment 约定磁盘布局。虚拟目录名是 v0（旧名 blackbox 会在启动时迁移）。

根典型物理位置
内部虚拟根 {hostDataDir}/v0/
外部虚拟根 {hostExternalFilesDir}/v0/
Guest data .../v0/data/user/<userId>/<pkg>
Guest lib .../v0/data/app/<pkg>/lib
外部存储 .../v0/storage/emulated/<userId>/
伪造 /proc .../v0/proc/<appPid>/

路径已含 /v0/ 或 /blackbox/ 时，isVirtualPath 判定为已是物理路径，不再二次映射，避免循环。

生命周期

1
宿主启动
BEnvironment.load() 建 v0 树并迁移 legacy；HookManager 注入 OsStub。
2
Guest bindApplication
NativeCore.init(SDK_INT) → IOCore.enableRedirect(packageContext)。
3
填规则
组装 data / lib / user_de / profiles / sdcard / proc 映射，addRedirect 写入 Trie 并 mkdirs。
4
打开 IO 钩子
NativeCore.enableIO() 安装 UnixFileSystemHook 等；之后所有路径访问走重定向。 
BActivityThread.handleBindApplication
  ├─ NativeCore.init(api)
  ├─ IOCore.enableRedirect(ctx)
  │    ├─ addRedirect / addBlackRedirect
  │    └─ NativeCore.enableIO()
  └─ Application 创建 / ContentProvider

规则表

假设 Guest 包名 com.example.app，虚拟 userId = 0，宿主 systemUserId = 0。

逻辑前缀物理目标
/data/data/<pkg>/lib
/data/user/<sysUid>/<pkg>/lib		 {v0}/data/app/<pkg>/lib
/data/data/<pkg>
/data/user/<sysUid>/<pkg>		 {v0}/data/user/<userId>/<pkg>
/data/user_de/<sysUid>/<pkg> {v0}/data/user_de/<userId>/<pkg>
/data/misc/profiles（及 cur/ref） {v0}/profiles/...
/sdcard
/storage/emulated/<sysUid>		 {ext}/v0/storage/emulated/<userId>/
（可选）/system/bin/su 等 *-fake
/proc/self/{cmdline,maps,status} {v0}/proc/<appPid>/...

/proc 特殊处理

  • maps：过滤含 sandhook / blackbox 的行后再映射。
  • status：把 PPid 伪造成 zygote，避免 VA 扫描顺着父进程找到宿主包名。

黑名单

/sdcard/Pictures 等走 addBlackRedirect，命中后短路，避免被整盘 sdcard 规则拖走。

同一 orig 前缀只加一次（已存在则跳过），进程内不可热更新同前缀。

解析算法

IOCore.redirectPath(String) 顺序：

  1. 空路径 → 原样返回
  2. BEnvironment.isVirtualPath（含 /v0/ 或 /blackbox/）→ 不再映射
  3. 黑名单 Trie 命中 → 短路返回
  4. 重定向 Trie 找最长合法前缀（按 / 边界，避免 /data/data/foo 误伤 foobar）
  5. 物理前缀 + 原路径后缀
  6. 否则原路径
输入: /data/data/com.example.app/files/a.db
键:   /data/data/com.example.app
输出: /data/user/0/<host>/v0/data/user/0/com.example.app/files/a.db

输入: /sdcard/Download/x.png
键:   /sdcard
输出: .../Android/data/<host>/files/v0/storage/emulated/0/Download/x.png

两条生效通道

1. Java：OsStub

代理 libcore.io.Os。在 invoke 里把所有以 / 开头的 String 参数改成 IOCore.redirectPath(...)。open / stat / access / chmod 等凡走 Os 的路径都会被改写；顺带伪造 getuid、stat.st_uid。

2. Native：UnixFileSystemHook

Hook java.io.UnixFileSystem 的 canonicalize0、list0、createDirectory0、createFileExclusively0 等，调用前经 JNI 回桥到 Java IOCore。

组件状态
OsStub有效
UnixFileSystemHook有效（部分方法需确认是否全部注册）
FileSystemHook（libc open）只查符号，未真正挂接
IO::redirectPath(const char*)规则表有写入，当前几乎无调用方

Guest 视角 vs 磁盘视角

对 Guest 而言，重定向是透明的：

  • Context.getFilesDir()、new File("/data/data/...") 仍是标准路径字符串
  • 真正 open 时已被改到 v0
  • getVisibleDataDir / getVisibleSourceDir 负责对外暴露「看起来像真机」的路径

对宿主磁盘而言，数据都在：

/data/user/0/<hostPkg>/v0/
├── data/user/<uid>/<guestPkg>/
├── data/app/<guestPkg>/
├── profiles/
└── proc/<pid>/

/storage/emulated/0/Android/data/<hostPkg>/files/v0/
└── storage/emulated/<uid>/...

如何观察

工程内没有 UI 规则表，也没有逐条 Java 映射日志。调试时可：

  • 直接看宿主磁盘上的 v0 树
  • logcat 过滤 NativeCore（addIORule / enableIO）
  • 临时在 IOCore.redirectPath 打采样日志

当前边界

  • 无完整 libc openat / stat 级重定向；纯 native 直调 libc 可能绕过。
  • Java 与 Native 规则双份，真相源在 Java。
  • 黑名单命中返回 Trie 匹配前缀，语义偏短路而非「原样放行」。
  • 不用 mount：无 root / 系统特权时不可用；有特权时 mount 通常更干净。
