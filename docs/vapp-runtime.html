BBA 里的 VApp 怎么跑起来

VApp 是装进沙箱的那一份应用。系统里看不到它，真正活着的是宿主名下的一个桩进程；进程起来之后，再换上访客自己的 Application、组件和数据目录。

是什么 三种进程 身份 装进去 点开之后 换上真应用 组件桩 虚拟系统 路径 Native 目录

是什么

BBA（界面名 BlackBox）是一个应用分身沙箱。宿主包名 com.android.bba，引擎包名 com.android.bb。同一份 APK 可以开多份，份与份之间用用户号 userId 分开，0 是第一份。

代码里这份访客叫 BAppClient。它不是系统安装器装出来的独立应用：包信息记在宿主自己的包数据库里，Activity、Service、Provider 都先落到宿主 Manifest 里预先声明的桩组件，再在桩进程里还原成访客真正的类。

内核看到的 uid 始终是宿主的 uid。访客以为自己有独立包名、独立进程名、独立数据目录，这些是 Java 层改写和路径重定向做出来的。

三种进程

BlackBoxCore.doAttachBaseContext 用进程名把当前进程分成三类。

Main

进程名固定为 com.android.bba。界面、装包、启动分身、Spindle 的 TCP 监听都在这里。

Server

进程名以 black_box_service_name 结尾。SystemCallProvider.onCreate 拉起 BlackBoxSystem，虚拟包管理、活动栈、用户、账号、定位、通知都住在这个进程。

VApp

其余进程，也就是 com.android.bba:p0 到 :p49。一个槽位跑一个访客进程。BActivityThread 在这里完成绑定。

槽位一共 50 个，ProxyManifest.FREE_COUNT。每个槽位在 Manifest 里配齐一套 ProxyActivity$P<n>、ProxyService$P<n>、ProxyJobService$P<n>、ProxyContentProvider$P<n>，并且 android:process=":p<n>"。系统要启动这个进程时，只要碰一下对应的 ContentProvider，进程就会被拉起来。

主进程第一次需要虚拟服务时，会确认 Server 进程在跑。Server 没起来就先启动它；服务 Binder 拿不到时，主进程会放一份本地的 fallback 服务顶上。

一份 VApp 的身份

进程记录是 ProcessRecord，交给访客的是可跨进程的 AppConfig。

字段含义
packageName访客包名，例如 com.example.app
processName访客自己的进程名。默认等于包名，多进程应用会带上 :push 这类后缀
userId分身号。界面分页的第几份，从 0 开始
bpid桩槽位，0 到 49。对应进程名 com.android.bba:p<bpid>，不是 Linux pid
buid虚拟 appId，由包管理器分配。进程表的键是 userId * 100000 + appId
uid真实 uid，也就是宿主 uid
callingBUid把这次启动发起者映射回虚拟 appId，供后续调用方身份使用

同一个包名、同一个 userId、同一个 processName 只会占一个槽。已经绑定过的进程直接复用，正在初始化的会在 initLock 上等到 BActivityThread 回传 Binder。50 个槽都占满时，startProcessLocked 抛出 No processes available。

装进去

界面调用 BlackBoxCore.installPackageAsUser。源可以是本机已安装应用的 sourceDir，也可以是一份 APK 文件或 Uri。宿主不允许安装自己，避免套娃。

请求进到 Server 进程的 BPackageManagerService，再交给 BPackageInstallerService，按顺序执行三个步骤：

1
CreateUserExecutor。保证这个 userId 在虚拟用户表里存在。
2
CreatePackageExecutor。解析 APK，写入包数据库，记下组件、权限和 appId。
3
CopyExecutor。把 APK 和原生库放到沙箱目录。之后查到的 ApplicationInfo.sourceDir 指向这份拷贝。

对外给出 ApplicationInfo 时，PackageManagerCompat.generateApplicationInfo 把数据目录改写成沙箱路径：dataDir 是 blackbox/data/user/<userId>/<包名>，deviceProtectedDataDir 是 data/user_de/...。非系统安装的包，nativeLibraryDir 指向 blackbox/data/app/<包名>/lib。

点开之后

BlackBoxCore.launchApk(packageName, userId) 向虚拟包管理器要启动 Intent，再交给 BActivityManager。Server 里的 ActivityStack.startActivityLocked 用虚拟包信息解析 Activity，并按 launchMode、taskAffinity、FLAG_ACTIVITY_NEW_TASK、CLEAR_TOP、SINGLE_TOP 维护自己的任务栈。命中已有栈顶时走 handleNewIntent，不再新建进程。

需要新界面时，startActivityProcess 做两件事：先确保目标进程活着，再造一个系统真正能启动的影子 Intent。

1
分配槽位。BProcessManagerService 扫一遍正在运行的 com.android.bba:p*，挑一个空闲的 bpid。
2
叫醒桩进程。ProviderCall 调用 com.android.bba.proxy_content_provider_<bpid> 的 _Black_|_init_process_，Bundle 里放着 AppConfig。这个 Provider 的 android:process 就是 :p<bpid>，所以系统会把该进程拉起来。
3
访客收下配置。ProxyContentProvider.call 把 AppConfig 交给 BActivityThread.initProcess，再把 IBActivityThread 这个 Binder 放回 _Black_|_client_。
4
Server 挂上死亡回调。Binder 断了就 onProcessDie：清进程表、删掉伪造的 cmdline、清掉这个包的通知。
5
造影子 Intent。组件换成 ProxyActivity$P<bpid>。主题是透明窗口时换成 TransparentProxyActivity$P<bpid>。真正的 Intent、ActivityInfo、userId、活动记录 Binder 塞进 extra：_B_|_target_、_B_|_activity_info_、_B_|_user_id_、_B_|_activity_record_v_。
6
交给系统。新任务用宿主 Context 的 startActivity，并带上 NEW_TASK。已有任务则通过系统 IActivityManager.startActivity，调用方包名写成宿主包名，这样系统检查的是宿主，不是尚未安装的访客。

桩进程里换上真应用

系统把 LAUNCH_ACTIVITY（Android 9 起是 EXECUTE_TRANSACTION）投进 ActivityThread.mH。HCallbackProxy 替换了这个 Handler 的 mCallback，在框架创建 Activity 之前改掉消息内容。

1
还没有 AppConfig。说明这次启动没有先走过 Provider 初始化。restartProcess 用当前进程补一次 initProcess，然后把消息插回队列头。
2
还没 bind。BActivityThread.bindApplication 在主线程执行 handleBindApplication。完成后同样把启动消息插回队列头，下一次再进回调时应用已经就绪。
3
替换启动参数。把事务里的 Intent 换成 _B_|_target_，ActivityInfo 换成访客的。Android 12 上还要把 ActivityClientRecord.packageInfo 设成已经换好的 LoadedApk。返回 false，框架按改过的参数创建真正的 Activity。

handleBindApplication 是 VApp 成型的地方，顺序固定：

1
取出访客包信息。从虚拟包管理器读 PackageInfo 和 Provider 列表。
2
换掉 ActivityThread 上的绑定数据。createPackageContext 得到访客的 LoadedApk，写回 mBoundApplication 的 appInfo、info、processName、providers。同时放行 mSecurityViolation，因为这段代码不是由系统安装器加载的。
3
改进程名。VirtualRuntime.setupRuntime 调用 Process.setArgV0(processName)，调试器看到的名字也改成访客进程名。目标 SDK 设成访客自己的 targetSdkVersion。
4
打开 Native 和 IO。NativeCore.init 记下 API 级别并准备路径回调。IOCore.enableRedirect 把数据目录、外置存储、/proc/self/cmdline 指到沙箱，然后 enableIO 装上 libc 层的 hook。
5
做出 Application。LoadedApk.makeApplication 走访客的 Application 类。makeApplication 失败时会再试一次强制创建。
6
onCreate 之前。安装访客自己的 ContentProvider，装上按包名登记的 HookEntry，并 NativeCore.spindleAgent(processName) 向 :black 里的 Spindle 注册这条进程。然后才调用 Application.onCreate。
ProxyActivity.onCreate 是钩子没改写事务时的退路：它立刻 finish，再把 extra 里的目标 Intent 重新 startActivity。正常路径上，框架创建的已经是访客 Activity，不会走进这个桩。

组件桩

系统只能启动 Manifest 里写过的组件，所以四种组件都有桩。桩的类名带槽位，保证组件和进程对得上。

访客组件系统看到的还原发生在
ActivityProxyActivity$P<n> 或透明变体HCallbackProxy.handleLaunchActivity 替换 Intent 和 ActivityInfo
ServiceProxyService$P<n>BActivityThread.createService 用访客 ClassLoader 构造真实 Service，再 attach 和 onCreate
JobServiceProxyJobService$P<n>同一套 createJobService
ContentProvider启动用的是桩 Provider绑定应用时 installProviders 安装访客自己的 Provider
BroadcastReceiver宿主里的 stub_receiverBActivityThread 在主线程构造接收者并 onReceive

Service 也有一条反向拦截：桩进程里如果系统要创建的 Service 不是本槽位的 ProxyService / ProxyJobService，HCallbackProxy.handleCreateService 会改走 BActivityManager.startService，由虚拟活动管理决定进哪个进程。

虚拟系统服务

Server 进程里 BlackBoxSystem.startup 只跑一次。它先建好 blackbox/ 目录，再让这些服务 systemReady：

服务访客以为自己在调
BPackageManagerService包的安装、解析、ApplicationInfo
BUserManagerService虚拟用户
BActivityManagerService活动、服务、广播、进程
BJobManagerServiceJobScheduler
BStorageManagerService存储卷
BPackageInstallerService安装和卸载流水线
BProcessManagerService槽位和进程生死
BAccountManagerService账号
BLocationManagerService定位，可按分身伪造坐标
BNotificationManagerService通知

主进程和 VApp 不直接 new 这些对象。它们通过 SystemCallProvider.call("VM") 按名字取 Binder，名字如 activity_manager、package_manager。客户端封装在 BActivityManager、BPackageManager 这一层。

HookManager.init 在 VApp 和 Server 进程里替换一批系统 Binder：活动、包、通知、定位、电话、网络、账号、存储、窗口、AppOps、WebView，以及小米相关服务。调用要么落到上面的虚拟服务，要么在参数里把访客包名、uid 改回宿主，让系统的权限检查通过。MethodParameterUtils 负责这种改写：已安装的包名换成宿主包名，虚拟 uid 换成宿主 uid。

路径

Java 侧 IOCore 用一棵前缀树保存规则，NativeCore.addIORule 把同一条规则交给 native。规则在 enableRedirect 里按当前访客填好，然后 enableIO 才真正挂钩。已经位于 /blackbox/ 下的路径不再改写。

访客看到的实际落到
/data/data/<包名>、/data/user/<系统用户>/<包名>ApplicationInfo.dataDir，即 blackbox/data/user/<userId>/<包名>
上面两个路径的 /libnativeLibraryDir
/data/misc/profilesblackbox/profiles，并按 userId 和包名拆出 cur / ref
/sdcard、/storage/emulated/<系统用户>外部存储/blackbox/storage/emulated/<userId>/
/proc/self/cmdline、/proc/<pid>/cmdlineblackbox/proc/<bpid>/cmdline，内容是访客进程名

/sdcard/Pictures 在黑名单里，不跟随整盘重定向。设置里打开隐藏 Root 时，常见的 su 路径会被指到一个不存在的 *-fake 路径。

同一套规则还要从 libc 生效，否则访客用 native 打开文件会绕过 Java。所以 enableIO 之后会挂钩文件系统、UnixFileSystem、DexFile、VMClassLoader、Binder 和 zlib。

Native

libbba.so 在 JNI_OnLoad 里注册 NativeCore 的本地方法。init 只做准备：记下 API 级别、缓存 redirectPath 和 getCallingUid 的方法 ID，初始化 JNI hook，并在主进程里启动 Spindle。真正的 inline hook 推迟到 enableIO，也就是 VApp 绑定应用的时候。

符号用 xdl 解析，跳转用 Dobby。另外会关掉 hidden API 检查。属性伪装把一部分 ro.* 改成 Pixel 6 / Android 12 的值。

arm64 上还静态链进 Capstone（只开 AArch64 反汇编）和 Frida Gum 的 Interceptor、Stalker。对应 JNI 是 gumReplace、gumRevert、gumStalkerFollow。Stalker 会把 libbba.so 自己的可执行段排除掉。armeabi-v7a 没有这层。

Java hook 是另一条线。HookEntry 在 Application.onCreate 之前按包名查找编译期登记的 AppHook。子类先准备 SandHook / Xposed 兼容层，再执行自己的 onHook。enabled() 为 false 的包不会安装。

开发机要往这个进程送脚本时，走 Spindle。VApp 在 onBeforeApplicationOnCreate 里已经用进程名注册过。通道本身见 Spindle 在 BBA 里怎么工作。

目录

虚拟根在宿主缓存目录的上一级，名字是 blackbox。外置根是 getExternalFilesDir("blackbox")。

blackbox/
  system/                  user.conf、uid.conf、accounts.conf、fake-location.conf、包配置
  cache/                   empty.apk 等运行时用的空包
  proc/<bpid>/cmdline      给访客看的进程名
  profiles/cur、profiles/ref
  data/app/<包名>/         base.apk 和 lib
  data/user/<userId>/<包名>/
  data/user_de/<userId>/<包名>/
外部存储/blackbox/storage/emulated/<userId>/
  Android/data/<包名>/
  Android/obb/<包名>/

清数据走安装器的 RemoveUserExecutor 再 CreateUserExecutor，只动这个用户号下的数据。强停调用 killPackageAsUser，按 userId + appId 找到进程并 killProcess。卸载在需要时再删掉应用本体。
