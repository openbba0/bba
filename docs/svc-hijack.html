如何劫持路径类 SVC

虚拟应用需要把 guest 眼里的 /data/user/0/<pkg> 落到宿主沙箱。 libc 符号 hook 挡不住手写 svc #0；本文说明 BBA 用 seccomp-bpf + SIGSYS 补上这层兜底。

为什么要劫持 两层拦截 seccomp 过滤器 SIGSYS 处理 安全页回放 与崩溃 SDK 共存 配置开关 日志与验证

为什么要劫持 SVC

在 AArch64 上，用户态进入内核的入口几乎都是一条 svc #0： 系统调用号放在 x8，参数放在 x0…x5。 常规路径是 App → libc（openat 等）→ SVC。 对抗性 guest 可以直接在自己的 so 里写 SVC，完全不经过 libc 符号表，于是纯 PLT / Interceptor hook 会漏掉。

BBA 关心的是带路径参数的一组 NR： openat、fstatat、faccessat、renameat、unlinkat、 mkdirat、readlinkat、statx 等。 目标只有一件事：在进内核前把路径改写成沙箱真实路径（走已有的 IO::redirectPath）。

Java 层

UnixFileSystem 等 Java NIO 路径，靠 Java hook 覆盖。

libc 层

Frida Gum Interceptor 替换 openat 等符号，覆盖大多数正常调用。

SVC 层

seccomp 对 raw SVC 发 SIGSYS，兜底绕过 libc 的写法。

两层拦截怎么叠

1
FileSystemHook（Gum）

file_system_hook.cpp 用 Gum 替换 libc 的 openat / open / fstatat 等；替换后先 IO::redirectPath，再调原 trampoline。 这是热路径，开销相对可控。

2
SeccompIo（可选）

设置页打开「Seccomp 路径重定向」后， IOCore 调 NativeCore.enableSeccompIo() → SeccompIo_install()。 之后无论是否走 libc，只要 SVC 的 NR 在白名单里，就会被 trap。

3
实际叠加效果

走 libc 的调用：先被 Gum 改路径，再进内核时仍会被 seccomp 拦一次（IP 不在安全页）。 这是「正确但贵」的双重覆盖；手写 SVC 则只有 seccomp 这一层。

seccomp-bpf 过滤器

安装入口在 SeccompIo_install()（hook/seccomp_io.cpp）。 先 PR_SET_NO_NEW_PRIVS，再 PR_SET_SECCOMP / SECCOMP_MODE_FILTER。 过滤器只做三件事：

  1. 非 AArch64 → ALLOW（防御性）。
  2. 指令指针落在「安全页」4K 范围内 → ALLOW（避免回放时二次 trap）。
  3. 系统调用号属于路径白名单 → SECCOMP_RET_TRAP；其余 → ALLOW。
// 伪代码：过滤器逻辑
if (arch != AARCH64)            return ALLOW;
if (ip ∈ safe_page[4K])         return ALLOW;
if (nr ∈ {openat, fstatat, …})  return TRAP;
return ALLOW;

IP 白名单用的是把 instruction_pointer 低 12 位清零后与安全页基址比较， 这样 stub 里任何一条指令发出的 SVC 都放行。

aarch64 上 newfstatat 的 NR 宏名是 __NR_newfstatat， 代码里把它别名成 __NR_fstatat，避免 NDK 头文件里没有旧名字导致编译失败。

SIGSYS 处理函数

SECCOMP_RET_TRAP 会向进程投递 SIGSYS（信号 31）， 携带 SA_SIGINFO。handler 从 ucontext_t 读寄存器：

寄存器含义
x8系统调用号
x0…x5参数（对 openat：dirfd / path / flags / mode…）
返回后的 x0handler 写回的返回值；内核已把 PC 指到 SVC 下一条

处理顺序：

  1. 确认是路径类 NR；否则从安全页原样回放或返回 -ENOSYS。
  2. 用线程局部缓冲调用 IO::redirectPath 改写 path 参数指针。
  3. 调用安全页上的 g_safe_syscall6 真正进内核。
  4. 把返回值写进 uc_mcontext.regs[0]，恢复执行。

重入用 thread_local g_in_handler 保护：handler 里若再触发路径 SVC （例如打日志），只做安全页回放、不再改写，避免死循环或误返回错误码。

安全页：如何避免二次 trap

若在 SIGSYS handler 里再次执行 svc #0，而 IP 仍落在普通代码段， 过滤器会再次 TRAP → 无限嵌套。解决办法是：

  1. mmap 一页匿名内存，写入一小段 AArch64 stub；
  2. mprotect(PROT_READ|PROT_EXEC)；
  3. 过滤器对「IP ∈ 该页」直接 ALLOW。
// stub 语义：long f(n,a0,a1,a2,a3,a4,a5)
mov x8, x0
mov x0, x1
mov x1, x2
mov x2, x3
mov x3, x4
mov x4, x5
mov x5, x6
svc #0
ret

机器码常量写在 kSafeSyscallStub[]，装载后 __builtin___clear_cache，再按函数指针调用。

与崩溃 SDK 共存

小红书等 App 会加载 sentry / shadowhook，在初始化时 sigaction 一批信号。若把 SIGSYS 设回默认处理， 下一次被 trap 的 openat 就会直接把进程杀掉（日志里常见 exited due to signal 31），界面表现为启动黑屏 / 闪退。

BBA 的应对：

  1. 安装过滤器之前，用 Gum 锁住 libc 的 sigaction / sigaction64。
  2. 对 sig == SIGSYS 的请求：吞掉 act，只在需要时把当前 handler 填进 oldact。
  3. 然后再注册自己的 seccomp_sigsys，并置 g_lock_sigsys = true。
只锁 SIGSYS，其它信号仍交给 guest；否则会和 ANR / crash 上报打架。

配置开关

这条路径默认关闭：对每个路径 SVC 做用户态 trap 成本不低，也可能和个别 ROM / SDK 冲突。

层级位置
设置 UIsetting.xml → seccomp_path_redirect
持久化BlackBoxLoader.mSeccompPathRedirect
配置接口ClientConfiguration.isSeccompPathRedirect()
启用时机IOCore 初始化 IO 重定向后调用 enableSeccompIo()

改开关后需要按提示重启模块进程，新 guest 进程才会装上过滤器。

日志与验证

开启后可用：

adb logcat | grep SeccompIo

典型输出：

SeccompIo: locked sigaction(SIGSYS)
SeccompIo: path SVC trap installed, safe_page=0x…
SeccompIo: in  openat dirfd=… path=/data/user/0/… flags=0x…
SeccompIo: out openat dirfd=… path=/data/user/0/com.android.bba/v0/… flags=0x…
SeccompIo: ret openat = 91
  • in：trap 时的原始参数
  • out：redirectPath 之后
  • ret：安全页回放的内核返回值

若只看到 path SVC trap installed 却没有 in/out， 说明当前构建还没打上参数日志，或 guest 根本没走到路径 SVC（极少见）。

小结

BBA 的 SVC 劫持不是改内核，也不是全局 ptrace： 而是用进程内 seccomp-bpf 把感兴趣的 NR 打成 SIGSYS， 在用户态改路径后再从「白名单 IP」的 stub 重新进内核。 Gum 覆盖常态 libc；seccomp 覆盖 raw SVC；再锁住 SIGSYS 的 sigaction，避免崩溃 SDK 把陷阱变成自杀开关。

相关源码： core/src/main/cpp/hook/seccomp_io.cpp、 file_system_hook.cpp、 io.cpp； 设置入口见 App 模块 SettingFragment。
